# 1. はじめに

## 1.1 セキュリティ技術を向上させるために

近年、サイバー攻撃はますます高度化・巧妙化しており、企業のシステムやサービスを安全に運用するためには、さまざまな脆弱性への理解が必要になっています。

セキュリティ対策というと、ファイアウォールやWAFによる通信制御、ウイルス対策ソフトの導入、アクセス制御など、攻撃を防ぐための仕組みを思い浮かべる方も多いと思います。

もちろん、これらの対策は重要です。しかし、効果的なセキュリティ対策を実施するためには、攻撃者がどのような仕組みでシステムに侵入し、どのように脆弱性を悪用するのかを理解しておくことも重要です。

例えば、バッファーオーバーフローという脆弱性があります。

これは、プログラムが確保したメモリ領域の範囲を超えてデータを書き込んでしまう問題です。単純にプログラムが異常終了するだけでなく、メモリ上のデータやプログラムの実行制御に影響を与え、場合によっては攻撃者に任意のコードを実行される可能性があります。

このような攻撃の仕組みを理解していなければ、ソースコードを確認したときに何が危険なのかを判断したり、適切な対策を検討したりすることは難しくなります。

つまり、セキュリティ技術を向上させるためには、防御技術だけでなく、攻撃者の視点から脆弱性の仕組みを理解することも重要です。

そこで今回は、実際の攻撃手法を学び、技術力を高めることを目的として、CTFへの参加に取り組むことにしました。

## 1.2 CTFとは？

CTFとは、Capture The Flagの略称で、情報セキュリティに関する技術や知識を使って問題を解き、隠された文字列（Flag）を見つけ出す競技です。

一般的なCTFでは、問題ごとにFlagと呼ばれる文字列が用意されています。

参加者は、与えられたプログラムやファイル、Webサイト、通信データなどを調査し、脆弱性の発見や暗号の解読、プログラムの解析などを行います。そして、問題を解くことで発見したFlagを専用の入力欄に提出します。

例えば、次のような文字列がFlagとして設定されています。

```text
picoCTF{example_flag}
```

Flagを正しく提出すると、その問題をクリアしたことになります。

CTFは単に知識を問う試験とは異なり、実際にツールを使って調査・解析し、試行錯誤しながら答えを導き出す実践的な競技です。

### CTFの主な問題ジャンル

CTFにはさまざまなジャンルがあり、代表的なものを紹介します。

| ジャンル | 内容 |
|---|---|
| Web Exploitation | Webアプリケーションの脆弱性を発見し、認証回避や不正なデータ取得などを行う |
| Cryptography | 暗号方式や実装上の問題を分析し、暗号化されたデータを解読する |
| Reverse Engineering | 実行ファイルなどを解析し、プログラムの処理内容や隠された情報を特定する |
| Forensics | ファイルやメモリ、ネットワーク通信などの痕跡を調査し、必要な情報を見つける |
| Binary Exploitation | プログラムのメモリ管理や入力処理の脆弱性を利用し、プログラムの実行制御を奪う |
| General Skills | Linuxコマンド、ファイル操作、スクリプトなど、基本的な技術を使って問題を解く |

このように、CTFではWeb、ネットワーク、暗号、OS、プログラミングなど、幅広い分野の知識が必要になります。

今回の記事では、特にBinary Exploitationに注目します。

Binary Exploitationは、バイナリファイルの脆弱性を利用して、プログラムの実行制御を奪うことを目的とするジャンルです。

スタックバッファーオーバーフローやヒープ攻撃など、メモリの構造やプログラムの実行制御に関する低レイヤーの知識が必要になります。

picoCTFも、セキュリティ技術を競う大会の一つです。

# 3. ヒープバッファーオーバーフローによる制御奪取

## 3.1 ヒープ領域とは？

2章では、スタック領域に発生するバッファーオーバーフローを取り上げました。

今回は、もう一つの重要なメモリ領域であるヒープ領域について説明します。

プログラムが実行されると、メモリ上にはコードやデータを格納するための領域が用意されます。

代表的なものとして、次のような領域があります。

| メモリ領域 | 主な用途 |
|---|---|
| Text領域 | プログラムの機械語命令を格納する |
| Data領域 | 初期化済みのグローバル変数や静的変数を格納する |
| BSS領域 | 初期化されていないグローバル変数や静的変数を格納する |
| Heap領域 | 実行中に動的に確保するメモリを格納する |
| Stack領域 | 関数のローカル変数や戻り先などを管理する |

スタック領域は関数の呼び出しや終了に合わせて自動的に管理されますが、ヒープ領域はプログラムが必要に応じてメモリを確保・解放します。

C言語では、主に以下の関数を利用します。

| 関数 | 処理 |
|---|---|
| malloc() | 指定したサイズのメモリを確保する |
| calloc() | メモリを確保し、内容を0で初期化する |
| realloc() | 確保済みメモリのサイズを変更する |
| free() | 確保したメモリを解放する |

例えば、次のようなプログラムです。

```c
#include <stdio.h>
#include <stdlib.h>

int main(void) {
    char *buffer;

    // 100バイトのメモリを確保
    buffer = malloc(100);

    if (buffer == NULL) {
        return 1;
    }

    // 確保したメモリを使用
    buffer[0] = 'A';

    // メモリを解放
    free(buffer);

    return 0;
}
```

`malloc(100)`を実行すると、ヒープ領域から100バイト分のメモリを確保し、その先頭アドレスが返されます。

プログラムは返されたポインタを使って、確保したメモリにデータを書き込みます。

使用が終わったら`free()`で解放します。

このように、ヒープ領域はプログラムの実行中に動的にメモリを管理するための領域です。

## 3.2 ヒープ領域のメモリ管理

ヒープ領域の特徴を理解するうえで重要なのが、メモリの確保と解放を管理する仕組みです。

Linux環境で一般的に使用されるglibcでは、malloc/freeなどの関数を通じてメモリの管理を行います。

ただし、`free()`を実行したからといって、メモリ上のデータが直ちに消去されるわけではありません。

解放されたメモリは、再利用できるように管理されます。

このとき、glibcは確保・解放されたメモリ領域をサイズなどに応じて分類し、再利用するためのリストを管理しています。

この管理構造を理解することが、ヒープを利用した攻撃を理解するうえで重要になります。

### チャンク（Chunk）

glibcのmallocでは、ヒープ領域をチャンク（Chunk）という単位で管理します。

チャンクには、管理情報（メタデータ）と、プログラムが利用するデータ領域があります。

概念的には、次のような構造です。

```text
+---------------------------+
| Chunk A                   |
+---------------------------+
| prev_size                 |
+---------------------------+
| size                      |
+---------------------------+
| User Data                 |
|                           |
+---------------------------+

+---------------------------+
| Chunk B                   |
+---------------------------+
| prev_size                 |
+---------------------------+
| size                      |
+---------------------------+
| User Data                 |
|                           |
+---------------------------+
```

実際のチャンク構造では、隣接チャンクとの関係やフラグなども管理されています。

また、チャンクの管理情報の一部は、隣接するチャンクの状態によって利用方法が変わります。

重要なのは、プログラムが利用するデータ領域だけでなく、その周辺にもメモリ管理に必要な情報が存在するという点です。

もしバッファーオーバーフローによって、この管理情報を書き換えてしまうと、メモリ管理の動作そのものに影響を与える可能性があります。

### tcache（Thread Local Cache）

glibcには、メモリ確保・解放を高速化するための仕組みとして、tcache（Thread Local Cache）があります。

tcacheは、スレッドごとに管理されるメモリ領域の再利用リストです。

主に小さなサイズのチャンクを対象としており、解放されたチャンクを一時的に保持しておくことで、次回のmalloc時に再利用できるようにしています。

例えば、同じサイズのメモリを2つ確保したとします。

```c
void *a = malloc(0x20);
void *b = malloc(0x20);
```

その後、次のように解放します。

```c
free(a);
free(b);
```

この場合、tcacheには解放されたチャンクが登録されます。

tcacheは基本的に単方向リンクリストで管理され、後から解放したチャンクがリストの先頭になります。

概念的には次のようになります。

```text
tcache
  |
  v
+-------+      +-------+
| Chunk B| ---> | Chunk A| ---> NULL
+-------+      +-------+
```

次に同じサイズのメモリを`malloc()`で要求すると、tcacheの先頭にあるチャンクから再利用されます。

```text
malloc()
   |
   v
+-------+      +-------+
| Chunk B| ---> | Chunk A| ---> NULL
+-------+      +-------+
```

Chunk Bが返され、tcacheの先頭はChunk Aになります。

このように、tcacheはメモリの再利用を効率化する仕組みです。

一方で、このリンクリストの管理情報が不正に書き換えられると、mallocが本来想定していないメモリアドレスを返してしまう可能性があります。

ここが、今回取り上げるTcache Poisoningのポイントです。

## 3.3 Tcache Poisoningとは？

Tcache Poisoning（Tcache Poisoning Attack）は、tcacheが管理しているリンクリストの情報を不正に書き換えることで、malloc()に本来とは異なるメモリアドレスを返させる攻撃手法です。

通常、tcacheは解放済みチャンクをリンクリストで管理しています。

そのリンク先が書き換えられてしまうと、次にmalloc()を実行した際に、攻撃者が意図したアドレスが割り当て先として扱われる可能性があります。

つまり、単に確保したメモリの範囲を超えてデータを書き込むだけではなく、メモリ管理の仕組みそのものを悪用する攻撃です。

### Tcache Poisoningの基本的な仕組み

tcacheの各エントリーには、次に参照するチャンクのアドレスが管理されています。

このリンク情報が不正に書き換えられると、malloc()が次のチャンクを取得する際に、想定外のアドレスを参照することになります。

攻撃の流れを概念的に示すと、次のようになります。

**1. メモリを確保する**

```text
malloc()
   |
   +----> Chunk A
   |
   +----> Chunk B
```

**2. メモリを解放する**

```text
tcache

Chunk B ---> Chunk A ---> NULL
```

**3. 解放済みチャンクのリンク情報を書き換える**

```text
tcache

Chunk B ---> 攻撃者が指定したアドレス
```

**4. malloc()を実行する**

```text
malloc()
   |
   +----> Chunk B
   |
   +----> 攻撃者が指定したアドレス
```

この結果、本来はヒープ領域から返されるはずのポインタが、別のメモリ領域を指す可能性があります。

例えば、スタック上の変数など、別のメモリ領域を指すように操作できれば、その領域へのアクセスを通じてプログラムの動作に影響を与えられます。

ただし、任意のアドレスを指定できれば必ず攻撃が成立するわけではありません。メモリのアラインメントやglibcのバージョンによる検査など、さまざまな条件があります。

### Use After Freeとの関係

Tcache Poisoningを理解するうえで、Use After Free（UAF）という脆弱性も重要です。

UAFとは、解放済みのメモリ領域をプログラムが引き続き使用してしまう脆弱性です。

例えば、次のようなコードです。

```c
char *buffer = malloc(100);

free(buffer);

// 解放済みメモリへのアクセス
buffer[0] = 'A';
```

`free()`を実行した時点で、bufferが指していたメモリ領域は解放されています。

しかし、ポインタ自体は自動的に無効化されるわけではありません。

そのため、解放後も同じポインタを利用してしまうと、解放済みチャンクの内容を書き換えてしまう可能性があります。

tcacheに登録されたチャンクでは、チャンクのユーザーデータ領域の先頭部分がリンク管理情報として利用されます。

そのため、UAFによって解放済みチャンクを書き換えられる状態になると、tcacheのリンク情報を改ざんする攻撃につながる可能性があります。

なお、Tcache Poisoningの成立条件はUAFだけではありません。ヒープオーバーフローなどによって管理情報を書き換えられる場合もあります。

各攻撃手法について、glibcのバージョンごとにサンプルが用意されており、ヒープ管理の仕組みや攻撃成立の条件を確認できます。

GitHub：

### 3.4.1 実行環境の確認

まず、実行環境のglibcのバージョンを確認します。

glibcはバージョンによってヒープ管理の仕組みやセキュリティ対策が異なります。

特にglibc 2.32以降では、Safe-Linkingという仕組みが導入されています。

そのため、how2heapのサンプルを実行するときには、サンプルが対象としているglibcのバージョンと実行環境を合わせる必要があります。

how2heapでは、バージョンごとにディレクトリが分かれています。

例えば、次のような構成です。

```text
how2heap/

  +-- glibc_2.23/
  |
  +-- glibc_2.27/

  +-- glibc_2.31/
  |

```

### 3.4.2 サンプルプログラムの動作

Tcache Poisoningの基本的なサンプルでは、次のような処理が行われます。

1. malloc()で複数のメモリ領域を確保する
2. 確保したメモリ領域をfree()で解放する
3. tcacheに登録されたチャンクのリンク情報を変更する
4. malloc()を複数回実行する
5. 本来のヒープ領域とは異なるアドレスが返されることを確認する

重要なのは、malloc()が返すポインタは、通常であればmallocが管理するヒープ領域内のメモリを指すという点です。

しかし、tcacheのリンク情報が不正に書き換えられていると、malloc()が別のアドレスを返す場合があります。

how2heapのglibc 2.31向けサンプルでは、スタック上の変数のアドレスを利用し、malloc()がそのアドレスを返すことを確認しています。

つまり、攻撃によってmalloc()のメモリ割り当て先を操作できることを実証しています。

### 3.4.3 攻撃が成立する理由

なぜ、このようなことが可能なのでしょうか。

ポイントは、解放済みチャンクのデータ領域が、tcacheのリンク情報として再利用されていることです。

通常、プログラムが使用しているメモリ領域では、データを自由に読み書きできます。

しかし、free()を実行した後は、その領域はメモリ管理機構によって再利用可能な状態になります。

tcacheでは、解放済みチャンクの先頭部分に次のチャンクへのポインタが格納されます。

この情報が書き換えられると、tcacheのリンクリストが不正な状態になります。

そして、その状態でmalloc()が実行されると、malloc()は不正なリンク情報をもとに次のメモリ領域を取得しようとします。

結果として、攻撃者が意図したアドレスを返させることが可能になります。

この攻撃は、メモリ管理機構が内部で利用しているデータ構造を悪用している点が特徴です。

## 3.5 Safe-Linkingによる対策

ここまで説明したTcache Poisoningは、tcacheのリンク情報を書き換えることによって成立する攻撃です。

しかし、glibcでは、このような攻撃を難しくするための対策が導入されています。

その代表的なものがSafe-Linkingです。

Safe-Linkingは、glibc 2.32で導入された仕組みで、tcacheやfastbinの単方向リンクリストに格納されるポインタを保護します。

従来のように、リンク情報に次のチャンクのアドレスをそのまま格納するのではなく、格納位置のアドレス情報を利用してポインタを符号化します。

概念的には、次のような計算です。

```text
encoded_pointer = pointer XOR (storage_address >> 12)
```

実際の実装では、`PROTECT_PTR`というマクロで処理されています。

これにより、攻撃者がリンク情報を単純に書き換えただけでは、正しいポインタとして扱われにくくなります。

また、Safe-Linkingによって保護されたポインタを正しく操作するためには、格納位置のアドレスなどの情報が必要になります。

そのため、ヒープアドレスの情報漏えい（Heap Leak）が攻撃成立の重要な条件になる場合があります。

### Safe-Linking導入前後の違い

| 項目 | Safe-Linking導入前 | Safe-Linking導入後 |
|---|---|---|
| ポインタの格納 | 次のチャンクのアドレスをそのまま格納 | アドレス情報を利用して符号化 |
| リンク情報の改ざん | 比較的単純な書き換えで成立する場合がある | 正しい符号化が必要 |
| アドレス情報 | 条件によって不要 | ヒープアドレスの情報が必要になる場合がある |
| 攻撃の難易度 | 比較的低い | 高くなっている |

ただし、Safe-LinkingはTcache Poisoningを完全に防ぐものではありません。

ヒープアドレスの情報漏えいや、別の脆弱性を組み合わせることで、対策を回避する攻撃手法も研究されています。

実際にhow2heapにも、Safe-Linking導入後のglibcを対象としたTcache Poisoningや、Safe-Linkingの仕組みを解析するサンプルが用意されています。

そのため、glibcを新しいバージョンに更新することは重要ですが、それだけでヒープ攻撃を完全に防げるわけではありません。

## 3.6 ヒープ攻撃から学べること

今回のTcache Poisoningで重要なのは、ヒープ領域におけるメモリ管理の仕組みが、攻撃対象になるということです。

バッファーオーバーフローというと、確保したメモリ領域を超えてデータを書き込むだけの問題に見えるかもしれません。

しかし、実際には、その書き込みによってメモリ管理機構の内部データまで破壊される可能性があります。

また、UAFのように、メモリを解放した後の扱いを誤ることも、ヒープ攻撃につながります。

防御側の視点では、次のような点が重要になります。

- malloc()で確保したメモリのサイズを正しく管理する
- バッファーの境界を超えた書き込みを防止する
- free()したポインタを再利用しない
- メモリの所有権や寿命を明確にする
- AddressSanitizerなどを利用してメモリ関連の不具合を検出する
- glibcなどのライブラリを適切に更新する

特に、C言語やC++で開発されたプログラムでは、メモリ管理の不備が重大な脆弱性につながる可能性があります。

攻撃の仕組みを理解することは、ソースコードレビューや脆弱性診断を行う際にも役立ちます。

</WritingBlock}

<WritingBlock id="73182" variant="document"># 4. picoCTFに参加してみた

## 4.1 参加の目的

ここまで、スタックバッファーオーバーフローとヒープを利用した攻撃手法について説明してきました。

これらの技術は、メモリの構造やプログラムの動作を理解するうえで重要ですが、実際に攻撃を成立させるためには、ソースコードの解析、実行環境の調査、デバッガーによるメモリの確認など、複数の技術を組み合わせる必要があります。

そこで、実際のCTF問題に取り組み、これまで学習した知識を使って問題を解くことにしました。

今回の目的は、単にFlagを取得することではありません。

次の3点を意識して取り組みました。

1. **脆弱性を発見する力**：プログラムのソースコードや動作から、問題となる処理を見つける
2. **攻撃の仕組みを理解する力**：脆弱性がどのように悪用されるのかを考える
3. **解析ツールを使う力**：Linuxコマンドやデバッガーなどを活用して、実際の動作を確認する

特にBinary Exploitationでは、プログラムの動作を理解するだけでなく、メモリ上のデータがどのように配置され、どのように変化するのかを確認することが重要です。

## 4.2 picoCTFへの参加方法

picoCTFはWebブラウザーから利用できるため、基本的にはアカウントを作成すれば学習を始められます。

公式サイト：

https://picoctf.org/

練習問題に取り組む場合は、picoGymを利用します。

基本的な流れは次のとおりです。

1. picoCTFの公式サイトにアクセスする
2. アカウントを作成する
3. ログインして練習問題の一覧を確認する
4. 取り組みたいジャンルの問題を選択する
5. 問題文や配布ファイルを確認する
6. 必要なツールを利用して解析する
7. Flagを取得して提出する

問題によっては、ソースコードや実行ファイルが配布されるほか、リモート環境への接続情報が提供される場合もあります。

問題の内容に応じて、ローカル環境での解析とリモート環境での検証を使い分けます。

## 4.3 Binary Exploitationへの取り組み方

今回の記事ではBinary Exploitationを中心に取り上げました。

このジャンルでは、プログラムの脆弱性を発見し、メモリの状態や実行制御を解析することが求められます。

最初から攻撃コードを作成しようとするのではなく、まずは問題となるプログラムの動作を理解することが重要です。

### 解析の基本的な流れ

Binary Exploitationの問題では、次のような手順で解析を進めると整理しやすくなります。

**STEP 1：配布ファイルの確認**

まず、問題で配布されたファイルを確認します。

```bash
file ./chall
```

`file`コマンドを使うと、実行ファイルの形式やアーキテクチャなどを確認できます。

続いて、実行ファイルに含まれる文字列を確認します。

```bash
strings ./chall
```

エラーメッセージや処理内容を示す文字列などから、プログラムの動作を推測できる場合があります。

**STEP 2：保護機構の確認**

次に、実行ファイルに設定されているセキュリティ機構を確認します。

例えば、次のようなツールを利用できます。

```bash
checksec --file=./chall
```

主に確認する項目は以下のとおりです。

| 項目 | 概要 |
|---|---|
| RELRO | GOTなどの書き換えを制限する仕組み |
| Stack Canary | スタック上の不正な上書きを検出する仕組み |
| NX | データ領域でのコード実行を制限する仕組み |
| PIE | 実行ファイルのロードアドレスをランダム化する仕組み |
| ASLR | メモリ配置をランダム化する仕組み |

これらの保護機構を確認することで、どのような攻撃が成立する可能性があるのかを考える手掛かりになります。

**STEP 3：プログラムの動作を確認する**

次に、実際にプログラムを実行して、入力に対する動作を確認します。

```bash
./chall
```

入力値を変更したときの挙動や、異常終了する条件などを調べます。

ソースコードが配布されている場合は、入力処理やメモリ確保・解放の処理を重点的に確認します。

特に、以下のような処理には注意が必要です。

- 入力サイズのチェックが行われているか
- 配列やバッファーのサイズが適切か
- malloc()で確保したサイズと書き込みサイズが一致しているか
- free()したメモリを再利用していないか
- ポインタの参照先が適切に管理されているか

**STEP 4：デバッガーによる解析**

プログラムの動作を詳しく調べる場合は、GDBなどのデバッガーを利用します。

```bash
gdb ./chall
```

GDBでは、ブレークポイントを設定してプログラムを一時停止したり、レジスタやメモリの内容を確認したりできます。

例えば、以下のコマンドを利用します。

| コマンド | 用途 |
|---|---|
| break | ブレークポイントを設定する |
| run | プログラムを実行する |
| next | 次の行へ進む |
| step | 関数の内部に入る |
| info registers | レジスタの内容を確認する |
| x | メモリの内容を表示する |
| disassemble | アセンブリ命令を表示する |

Binary Exploitationでは、ソースコードだけでは分からない実際のメモリ配置やレジスタの状態を確認することが重要です。

GDBに加えてpwndbgなどの拡張を利用すると、スタックやヒープ、レジスタの状態を視覚的に確認しやすくなります。

## 4.4 参加して分かったこと

実際にCTFに取り組むことで、セキュリティ技術を学ぶ際には、単に攻撃手法の名称や手順を覚えるだけでは不十分であることが分かります。

例えば、バッファーオーバーフローという言葉を知っていても、実際に攻撃を成立させるためには、次のような知識が必要になります。

- メモリの構造
- CPUのレジスタ
- アセンブリ言語
- 関数呼び出しの仕組み
- OSやライブラリのメモリ管理
- コンパイラによる実行ファイルの生成方法
- セキュリティ機構の動作

これらは独立した知識ではなく、相互に関係しています。

例えば、スタックバッファーオーバーフローを理解するためには、関数呼び出し時のスタックフレームやリターンアドレスの仕組みを理解する必要があります。

また、ヒープ攻撃を理解するためには、malloc()やfree()の内部動作、glibcによるチャンク管理などの知識が必要になります。

一つの問題を解くために、複数の分野の知識を組み合わせる必要がある点が、CTFの難しさであり、学習する面白さでもあります。

### 攻撃者の視点で考えることの重要性

今回の学習で特に重要だと感じたのは、攻撃者の視点でプログラムを調査することです。

通常のプログラム開発では、入力されたデータを正しく処理できるか、想定した機能が動作するかという観点で確認することが多いと思います。

しかし、攻撃者は異なる視点でプログラムを見ています。

例えば、次のようなことを考えます。

- 想定外に大きなデータを入力したらどうなるか
- 解放済みのメモリを操作できたらどうなるか
- メモリ上の管理情報を書き換えられたらどうなるか
- プログラムの実行制御を変更できたらどうなるか
- セキュリティ機構が有効でも、別の脆弱性と組み合わせて回避できないか

このような視点を持つことで、通常の動作確認では見つけにくい問題にも気づけるようになります。

防御側としても、攻撃者がどこに着目し、どのような手順で脆弱性を悪用するのかを理解することが重要です。

## 4.5 今後の学習について

今回取り組んだBinary Exploitationは、セキュリティ技術の中でも比較的低レイヤーの知識が求められる分野です。

一方で、今回学んだメモリ管理やプログラムの実行制御に関する知識は、脆弱性診断やセキュアコーディングにも役立ちます。

今後は、Binary Exploitationだけでなく、Web ExploitationやForensicsなど、ほかのジャンルにも取り組んでいきたいと考えています。

また、今回のように攻撃手法を実際に試すだけでなく、脆弱性が発生する原因や、その対策についても理解を深めていきたいと思います。

セキュリティ対策を考えるうえでは、攻撃を防ぐ技術だけでなく、攻撃が成立する仕組みを知ることも重要です。

CTFは、その仕組みを実践的に学ぶことができる有効な学習方法の一つだと感じました。
